Two things in the logs that look like problems and are not:

  "... is group-readable — anyone in that group can authenticate as every label
  it holds" on every start. Kubernetes writes Secret files owned by root, the
  container runs as a non-root user, and the group is how the process is given
  the credential at all. rta leaves group read outside its refusal mask for
  exactly this case; it warns and starts.

  `rta doctor` reporting the data directory's permissions. fsGroup makes the
  volume group-writable, which is what makes it writable by the container at
  all. It is a doctor finding, not a startup refusal.

What is NOT picked up by editing values alone: nothing, but it is worth knowing
why. The roster and the token file are read once at startup, so the chart puts a
checksum of each in the pod annotations and a change restarts the pod. The one
exception is an operator key's `expires=`, which is checked per call against the
running clock - removing an expired key needs no restart, and restarting will
not be what evicted it.
